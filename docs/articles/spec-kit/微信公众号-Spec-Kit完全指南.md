## 开场：AI 很强，但「猜你想要什么」仍然很贵

你是不是也遇到过这种场景：

对 AI 说一句「帮我做一个相册应用」，它很快吐出一大坨代码——能跑一点，但总差那么点意思：登录怎么做？拖拽排序算不算？错误态谁管？技术栈是不是你团队要的？

再糟糕一点的版本是：

- 第一天生成了「完整应用」  
- 第二天加登录，把昨天结构打穿  
- 第三天改交互，AI 又重写了一遍状态管理  
- 第四天你开始怀疑：到底是我在写产品，还是在给 AI 擦地板？

GitHub 官方把前一种模式叫作 **vibe coding（凭感觉编程）**：看起来对，细看不对；适合 demo，不适合认真交付。

真正的问题通常不是「模型不会写代码」，而是：

1. **意图没被写清楚**——大量约束只存在于你脑子里  
2. **约束没有进入执行链路**——Wiki、群聊、口头约定，AI 用不上  
3. **缺少阶段性验收**——一次生成几千行，你只能整包认栽或整包重来  

GitHub 开源的 **Spec Kit**，就是为了把这件事扳回来——让**规格（Spec）成为可执行的真相源**，而不是写完就被丢掉的脚手架。

一句话定位：

> **你负责把「想清楚」；Spec Kit 负责把「想清楚」变成 AI 能稳定执行的流程。**

## 一、先把几个概念讲清楚（别再混着说）

很多高阅读量文章会把「SDD」「Spec Kit」「Specify CLI」「斜杠命令」混着说。其实它们是一层套一层的关系：

| 概念 | 它是什么 | 一句话定位 | 类比 |
| --- | --- | --- | --- |
| **Spec-Driven Development（SDD / 规范驱动开发）** | 一种开发方法论 | **先定义「做什么、为什么」，再让实现跟着规格走** | 交通规则 |
| **Spec Kit** | GitHub 开源工具包（MIT） | 把 SDD **落地成可复用流程**，适配 Copilot / Claude Code / Cursor 等 | 导航系统 |
| **Specify CLI（`specify`）** | Spec Kit 的命令行入口 | 负责 `init`、装模板、接 AI 集成、装扩展 | 导航 App 安装器 |
| **`/speckit.*` 命令 / Skills** | AI 助手里的工作流步骤 | 真正驱动「宪法 → 规格 → 方案 → 任务 → 实现」 | 逐段导航指令 |
| **Artifacts（产物文件）** | `constitution.md`、`spec.md`、`plan.md`、`tasks.md` 等 | 每一步留下**可审阅、可回退、可对齐**的 Markdown 真相 | 行程单与路书 |

![对比：左侧 vibe coding，右侧 Spec 驱动](./images/spec-kit-vs-vibe.jpg)

### 为什么现在才流行？

传统软件开发里，「代码是唯一真相」有道理——因为文档很难持续同步。  
但 AI 出现后，局面变了：

- **规格第一次变得「可执行」**：不再只是给人看的说明，而是能驱动计划、任务和实现  
- **变更成本下降**：改 Spec 再派生下游，往往比在几千行臆测代码里打补丁更划算  
- **组织知识终于有地方放**：安全策略、设计系统、合规要求，可以写进 Constitution / Plan，让 AI 真的用上  

GitHub Blog 的核心论断可以记一句：

> 我们不该把 coding agent 当搜索引擎；该把它当**字面意义很强的结对程序员**——它擅长模式补全，不擅长读心术。

## 二、Spec Kit 里「各自是什么」（含写法对照）

可以把 Spec Kit 想成一套「给 AI 的工程流水线」。主线命令如下（以官方当前形式 `/speckit.*` 为准）：

### 1. Constitution（项目宪法）——`/speckit.constitution`

**是什么**：项目级「非谈判原则」——质量底线、测试要求、体验一致性、性能红线、合规约束等。  
**产物**：通常是 `.specify/memory/constitution.md`。  
**特点**：一般**每个项目做一次**；原则变化时再修订（社区实践里常配合语义化版本：重大原则变更升 MAJOR，新增原则升 MINOR，措辞澄清升 PATCH）。

**好宪法长这样（节选示意）：**

```markdown
## 原则一：可测试的增量交付
- MUST：每个用户故事对应可独立验证的验收标准
- MUST：关键路径变更附带自动化测试或可复现手工验收步骤
- 理由：AI 容易「一次写完」，人需要「一次验完」

## 原则二：依赖最小化
- MUST：新增依赖前在 Plan 中写明理由与替代方案
- SHOULD：优先使用语言/平台内置能力
```

**差宪法长这样：**

```text
要高质量、高性能、高可用，代码优雅，大家都满意。
```

> 高赞实践与社区讨论的共识：**宪法要短、可判定、可执行**。写到上千行「百科全书」，模型反而更容易忽略。

### 2. Specify（规格）——`/speckit.specify`

**是什么**：用自然语言描述**用户旅程、成功标准、边界与非目标**。  
**关键纪律**：只写 **What / Why**，**不要在这里堆技术栈**。  
**产物**：`spec.md`（以及需求检查清单相关内容）。

**Specify 阶段建议覆盖的 6 块：**

1. 问题与目标用户  
2. 核心用户故事（按优先级）  
3. 成功指标 / 验收标准  
4. 边界情况与失败路径  
5. 明确的非目标（Out of Scope）  
6. 假设与待决事项（后面交给 Clarify）

**好输入示例：**

```text
/speckit.specify
为摄影爱好者做一个相册整理工具。
用户能创建相册、把照片加入相册、在主页拖拽调整相册顺序；
未登录可浏览示例数据，登录后才能创建与编辑。
成功标准：新用户 3 分钟内完成「创建相册并放入 3 张照片」。
非目标：本阶段不做云同步、不做社交分享、不做人脸识别。
请展开用户故事、边界与验收标准，不要选择技术栈。
```

**差输入示例：**

```text
/speckit.specify
用 React + NestJS + Postgres 做一个很酷的相册，最好还能 AI 自动分类。
```

后者的问题不是「不能做」，而是：你把 **How** 提前塞进了 **What**，后面 Plan 失去比较空间，Spec 也更容易变成技术说明书。

### 3. Clarify（澄清）——`/speckit.clarify`（质量门）

**是什么**：针对规格里含糊的地方，一次最多抛出约 5 个高影响问题，把你的回答**写回 spec**。  
**何时用**：需求有歧义、边界不清、生产级功能——强烈建议在 Plan 之前跑。  
**可重复**：每次可聚焦不同主题（权限 / 移动端 / 数据删除策略……）。

典型会被问到的问题：

- 删除相册时，照片是一并删除、回到「未分类」，还是禁止删除非空相册？  
- 拖拽排序是否需要在移动端手势支持？不支持算不算失败？  
- 「未登录可浏览示例」是只读副本，还是允许本地临时修改但不落库？

> **经验法则**：你无法在 30 秒内回答的问题，就不该让 AI 在实现时「随便猜」。

### 4. Plan（技术方案）——`/speckit.plan`

**是什么**：把「做什么」翻译成「怎么做」——技术栈、架构、集成约束、性能与合规要求。  
**产物**：`plan.md`，以及研究/设计类附属文档（如 `research.md` 等）。  
**特点**：公司强制技术栈、遗留系统对接、安全基线，都应该写在这里。

**Plan 里至少应看到：**

- 技术选型与「为什么选它 / 为什么不选它」  
- 关键模块与数据流  
- 与现有系统的集成点  
- 测试策略  
- 风险与缓解  

你也可以要求「同一 Spec 产出两套 Plan 变体」再做对比——这是 vibe coding 很难系统性做到的事。

### 5. Checklist（质量清单）——`/speckit.checklist`（质量门）

**是什么**：给「用自然语言写的需求」做单元测试式检查——完整性、清晰度、一致性。  
**比喻**：像给规格本身写测试。  
**注意**：实现前若清单未勾选，流程会提醒你先处理；别把 Checklist 当成可跳过的装饰。

### 6. Tasks（任务拆解）——`/speckit.tasks`

**是什么**：把 Spec + Plan 拆成**可独立实现、可单独验收**的小任务。  
**产物**：`tasks.md`（常见阶段：Setup → Foundational → 按用户故事分相 → Polish；可标记并行）。  
**为什么重要**：AI 最怕「做一个认证系统」这种巨型任务；它需要「创建校验邮箱格式的注册接口」这种粒度。

**任务粒度对照：**

| 过粗（容易翻车） | 更合适 |
| --- | --- |
| 做用户系统 | 实现邮箱注册接口：校验格式、重复邮箱返回 409、写集成测试 |
| 做相册首页 | 实现相册列表读取 API + 空状态 UI，手动验收「零相册时显示引导」 |
| 优化性能 | 为相册列表添加分页（默认 20），并补充慢查询说明 |

### 7. Analyze（交叉分析）——`/speckit.analyze`（质量门）

**是什么**：在动手写代码前，只读检查 Spec / Plan / Tasks 是否有遗漏、冲突、覆盖不足，并给出报告（通常不直接改文件）。  
**建议时机**：`tasks` 之后、`implement` 之前；实现后也可再跑一轮做审查。  
**发现问题怎么退回：**

- 需求问题 → 回到 `specify` / `clarify`  
- 设计问题 → 回到 `plan`  
- 拆分问题 → 重新 `tasks`  
- 然后再 `analyze`，直到干净

### 8. Implement（实现）——`/speckit.implement`

**是什么**：按 `tasks.md` 的依赖顺序执行实现（可分阶段，避免一次塞爆上下文）。  
**你的角色**：从「写一万行」变成「审一小块、验一小块」。  
**关键习惯**：大功能不要「一条命令打天下」，而要：

```text
/speckit.implement 只完成 Foundational 与用户故事 1，验证通过后停止。
```

### 9. Converge（收敛）——`/speckit.converge`

**是什么**：对照 Spec / Plan / Tasks 审查当前代码库，把缺口追加成新任务（append-only），再交回 Implement。  
**它通常不会**：直接改 Spec/Plan，或悄悄「帮你把需求改成现状」。  
**意义**：补上实现后反馈环，专门对付 **Spec Drift（规范漂移）**——代码越写越远、文档越来越假。

### 10. 周边能力（完整版地图）

| 能力 | 说明 | 什么时候用 |
| --- | --- | --- |
| `/speckit.taskstoissues` | 任务同步为 GitHub Issues | 多人协作、要看板跟踪 |
| **Bug 扩展** | `assess → fix → test` | 线上/集成缺陷，需要证据链 |
| **Assess 扩展** | `intake → research → define → shape → decide` | 还没决定「做不做」 |
| **Extensions** | 扩展能力包 | 定制组织流程 |
| **Presets** | 预设组合 | 快速套用团队习惯 |
| **Bundles** | 面向角色的一键配置 | 给 PM / 研发 / 安全等不同角色开工 |

## 三、它们之间是什么关系？

一句话：

> **人负责意图与把关，Spec Kit 负责把意图固化成产物，AI 助手负责在产物约束下写代码。**

![组件关系：意图 → 产物链 → AI 执行](./images/spec-kit-components.jpg)

### 1. 依赖关系（数据怎么流）

```text
Constitution（约束全局）
        ↓
Specify（定义目标） → Clarify（消歧，可选但推荐）
        ↓
Plan（技术落地） → Checklist（质量门，可选）
        ↓
Tasks（可执行切片） → Analyze（一致性门，可选）
        ↓
Implement（写代码） ⇄ Converge（对照规格收敛）
```

两条官方路径可以并存：

| 路径 | 步骤 | 适合 |
| --- | --- | --- |
| **最短主线** | Specify → Plan → Tasks → Implement → Converge | 原型、低歧义小功能 |
| **生产完整路径** | + Constitution、Clarify、Checklist、Analyze | 有风险、要协作、要长期维护 |

![工作流管道示意](./images/spec-kit-workflow.jpg)

### 2. 职责关系（谁管什么）

| 层级 | 管什么 | 不管什么 | 变更成本 |
| --- | --- | --- | --- |
| Constitution | 长期原则与红线 | 单个功能细节 | 低频率、高影响 |
| Spec | 用户价值与行为契约 | 具体框架选型 | 中（改了要派生下游） |
| Plan | 技术路径与约束 | 逐行代码 | 中 |
| Tasks | 可验收的工作切片 | 产品愿景本身 | 较低 |
| Implement | 交付可运行增量 | 偷偷改需求定义 | 高（若缺少上游对齐） |
| Converge | 发现缺口并回流任务 | 用代码现状覆盖 Spec | — |

### 3. 和「传统文档 / 其他方案」比，到底新在哪？

| 方案 | 优势 | 常见代价 | Spec Kit 补的那一刀 |
| --- | --- | --- | --- |
| 传统 PRD + 人工编码 | 灵活、团队熟悉 | 文档易过期，落地靠人肉翻译 | 规格进入执行链 |
| 纯 Prompt 生成 | 快 | 臆测多、难复盘 | 分阶段产物 + 验收点 |
| 低代码平台 | 更快出界面 | 定制与锁定风险 | 你仍拥有真实代码 |
| 敏捷流程 | 节奏成熟 | 多数步骤仍靠人写 | 在节奏里嵌入 AI 可执行规格 |

jqknono、博客园等高阅读解读文反复强调的本质是：

> **不是「多写了几份 Markdown」，而是「Markdown 成了可执行契约」。**

## 四、什么时候该用？场景、角色与收益

GitHub Blog 点名了三类最吃香的场景；中文实践文基本也围绕它们展开：

![三大场景：从 0 到 1、存量加功能、遗留现代化](./images/spec-kit-scenarios.jpg)

### 场景 A：Greenfield（从 0 到 1）

**痛点**：一上来就写代码，AI 会用「最常见模板」猜你的产品。  
**用法**：先 Constitution + Specify，把成功标准写死，再 Plan。  
**收益**：少返工，骨架更像「你的产品」而不是「通用脚手架」。  
**反模式**：第一天就让 AI「生成完整 App」，第二天再补 Spec——基本必改。

### 场景 B：存量系统加功能（N → N+1）——往往最值钱

**痛点**：新功能很容易「长成外挂」，和旧架构打架。  
**用法**：Spec 写清与旧系统的交互边界；Plan 写清必须遵守的架构约束与禁忌。  
**收益**：AI 生成的代码更「像本仓库的孩子」。  
**加分项**：把仓库里的架构文档、API 约定纳入 Plan 上下文。

### 场景 C：遗留系统现代化

**痛点**：业务意图散落在老代码、口头传统和过期 Wiki 里。  
**用法**：先用 Spec 捞出「必须保留的业务契约」，再用 Plan 设计新架构，最后 Implement 重建。  
**收益**：现代化时带走业务，不带走历史包袱。  
**提醒**：先 Assess（值不值得做）再 SDD，能少开很多天坑。

### 额外好用场景

- **快速原型**：最短路径跑通 Specify → Plan → Tasks → Implement  
- **多技术栈对照**：同一 Spec，换两套 Plan，比较实现代价  
- **合规/安全前置**：把硬约束写进 Constitution / Plan，而不是 Code Review 时再喊停  
- **Bug 修复**：用 bug 扩展走「评估 → 修复 → 验证」，避免「盲改一行碰运气」

### 不同角色怎么协作？

![产品、架构、研发围绕同一套产物协作](./images/spec-kit-roles.jpg)

| 角色 | 主要出手点 | 关键问题 |
| --- | --- | --- |
| 产品 / 业务 | Specify、Clarify、验收标准 | 用户到底怎样算成功？ |
| 架构 / Tech Lead | Constitution、Plan、Analyze | 约束是否可执行？会不会架构漂移？ |
| 研发 | Tasks 审查、Implement 分段、测试 | 每个任务能否独立验证？ |
| QA / 负责人 | Checklist、Converge、发布门禁 | 规格与实现是否闭合？ |

**团队最小闭环建议：**

1. Spec 由产品确认  
2. Plan 由架构确认  
3. Tasks 由执行者确认「可做完」  
4. 每个 Implement 片段都有人点头  
5. Converge 不过，就不叫「做完」

## 五、完整示例 A：相册整理（官方风格 Greenfield）

下面这个例子综合了官方 Quickstart 与多篇高阅读实践文的写法，可直接改成你的业务。

### Step 0：安装与初始化

```bash
# 安装 Specify CLI（建议钉版本，把 vX.Y.Z 换成最新 Release）
uv tool install specify-cli --from git+https://github.com/github/spec-kit.git@vX.Y.Z

# 初始化项目并接入你的 AI 助手（示例：Copilot）
specify init photo-album --integration copilot
cd photo-album

# 非交互环境（CI / Agent）可加：
# specify init photo-album --integration copilot --non-interactive
```

> 也可用 PyPI：`uv tool install specify-cli`。  
> Cursor / Claude Code / Gemini CLI 等按官方集成参数选择即可。  
> 已有仓库初始化：`specify init . --integration <你的助手>`；覆盖时注意保护自定义 constitution/templates。

### Step 1：写下项目宪法

```text
/speckit.constitution
创建一套原则：
1) 可读代码优先于炫技抽象；
2) 关键路径必须有测试或可复现验收；
3) UI 交互保持一致；
4) 首屏操作 100ms 内有反馈；
5) 禁止引入重型框架，除非 Plan 阶段明确批准并记录理由。
```

### Step 2：只谈产品，不谈技术栈

```text
/speckit.specify
我想做一个帮助整理照片的应用：
- 用户可以把照片放进不同相册
- 相册默认按日期分组
- 在主页支持拖拽重新组织相册
- 未登录也可浏览示例相册，登录后才能创建与编辑
成功标准：新用户 3 分钟内完成「创建相册并放入 3 张照片」
非目标：云同步、社交分享、人脸识别
请聚焦用户故事、边界情况与验收标准，先不要选择技术栈。
```

### Step 3：澄清歧义

```text
/speckit.clarify
重点澄清：拖拽冲突、删除相册时照片归属、移动端是否必须支持拖拽、
以及示例数据是否允许本地临时修改。
```

### Step 4：再谈怎么做

```text
/speckit.plan
技术方向：Vite + 尽量原生 HTML/CSS/JS；
本地优先存储；拖拽用成熟轻量方案；
需要说明数据模型、页面结构、测试策略、已知风险与回滚思路。
```

### Step 5：拆任务 → 分析 → 分段实现 → 收敛

```text
/speckit.tasks
/speckit.analyze
/speckit.implement 只实现数据模型与本地存储相关任务，验证后停止
/speckit.implement 实现相册列表与拖拽排序，验证后停止
/speckit.converge
```

若尚未 **Converged**，继续 Implement ↔ Converge。

### 产物长什么样？（示意）

**`spec.md` 片段：**

```markdown
### 用户故事 1 - 创建相册
作为登录用户，我希望创建相册并命名，以便开始整理照片。
验收：
- 名称长度 1..50
- 重名时提示并拒绝
- 创建成功后出现在列表顶部
```

**`tasks.md` 片段：**

```markdown
## Phase: Foundational
- [ ] T001 建立相册与照片的本地数据模型
- [ ] T002 实现本地持久化读写封装（含失败提示）

## Phase: US1 创建相册
- [ ] T010 实现创建相册用例与校验
- [ ] T011 实现创建成功后的列表刷新
```

## 六、完整示例 B：给现有电商后台加「优惠券」（Brownfield）

这是很多团队更真实的用法——仓库已经存在，你要安全地加功能。

### 1）先写清边界（Specify）

```text
/speckit.specify
在现有电商后台中新增优惠券管理能力：
- 运营可创建满减券 / 折扣券
- 可设置生效时间、库存、适用商品范围
- 下单时自动匹配最优可用券（本阶段仅单券）
- 需兼容现有订单服务，不改变现有支付流程
非目标：叠加券、异业券、直播专属券
请写清与现有订单/商品服务的交互契约与验收标准，不要改技术栈。
```

### 2）把「不能碰的东西」写进 Plan

```text
/speckit.plan
约束：
- 复用现有单体后台的模块边界与权限模型
- 优惠券校验必须在服务端，前端仅展示
- 订单服务 API 仅允许新增字段，不允许破坏旧客户端
- 提供迁移脚本与回滚方案
- 补充对账日志：发券、核销、作废
请输出模块划分、数据模型、序列图级数据流、测试与发布计划。
```

### 3）任务要「可回滚」

```text
/speckit.tasks
请确保任务按「数据迁移 → 领域服务 → 管理端 API → 下单接入 → 观测与回滚」排序，
并标记可并行项。
```

### 4）实现时按切片推进

```text
/speckit.implement 仅完成数据模型、迁移与管理端创建/查询，不做下单接入
# 人工验收后再继续
/speckit.implement 完成下单匹配与核销，并补齐关键路径测试
/speckit.converge
```

**Brownfield 额外检查清单：**

- [ ] Spec 是否写了「与旧系统的兼容承诺」？  
- [ ] Plan 是否写了「禁止事项」而不只是「要做事项」？  
- [ ] Tasks 是否包含迁移 / 回滚 / 观测？  
- [ ] Converge 是否专门核对了「旧客户端不受损」？

## 七、需求总会变：Living Spec 怎么演进？

![规格演进闭环：改 Spec → 对齐 Plan/Tasks → 实现 → Converge](./images/spec-kit-change-loop.jpg)

官方 evolving-specs 思路很明确：**`spec.md` 是契约，`plan.md` / `tasks.md` 是派生物。**

### 推荐变更顺序

1. **先改 Spec**（行为真的变了）  
2. 必要时 `/speckit.clarify`  
3. 更新或重跑 `/speckit.plan`  
4. 更新或重跑 `/speckit.tasks`  
5. `/speckit.analyze` 看是否还有缝  
6. 再 `/speckit.implement`  
7. `/speckit.converge` 收口  

### 三种常见变更类型

| 类型 | 例子 | 正确做法 |
| --- | --- | --- |
| 行为变更 | 「支持双券叠加」 | 先改 Spec，再派生 Plan/Tasks |
| 技术变更 | 「数据库从 SQLite 换 Postgres」 | Spec 可不动，重点改 Plan/Tasks |
| 执行纠偏 | 「任务粒度过粗」 | 改 Tasks，但若暴露了需求洞，要回流 Spec |

### 千万别这样

- 只改代码，不改 Spec → 文档撒谎  
- 只改 Tasks「把做不到的勾掉」→ 进度撒谎  
- 用 Converge 当借口，把现状写成需求 → 产品撒谎  

> **Flow-back 可以发生，但必须有纪律：下层发现的问题，最终要回到它真正归属的那一层。**

## 八、和「直接让 AI 写代码」差在哪？

| 维度 | 纯 Prompt / vibe coding | Spec Kit（SDD） |
| --- | --- | --- |
| 真相源 | 聊天记录与临时代码 | Spec / Plan / Tasks 文件 |
| 失败模式 | 看起来能跑、细节大量臆测 | 在 Plan/Tasks 阶段就暴露缺口 |
| 评审粒度 | 一次看上千行 | 按任务增量审阅 |
| 需求变更 | 推倒重来或补丁叠补丁 | 更新 Spec → 再生 Plan/Tasks |
| 组织知识 | 散落在 Wiki / 群聊 | 进入 Constitution 与 Plan，AI 真用得上 |
| 可追溯 | 很难回答「为什么这样实现」 | 从任务可回指到规格条款 |
| 适合 | Demo、探索、个人试错 | 要交付、要协作、要演进的功能 |

社区常把 Spec Kit 概括成：

> **给 AI 编程加「工程护栏」，而不是又一个代码生成器。**

## 九、避坑指南（来自官方文档 + 高阅读实践 + 社区讨论）

### 1. 宪法不是越长越好

过长的宪法容易变成「模型跳读」。  
**建议**：1～2 页可判定原则 + 少量治理条款；细则放到模板或 Plan。

### 2. 不要在 Specify 阶段选技术栈

过早绑死 React/Go/Kafka，会让需求讨论变成架构口水仗，也让「同一 Spec 多 Plan」失效。

### 3. 警惕「TODO = 完成」

社区真实反馈：任务被勾完，代码里却只剩 `// TODO`。  
**对策**：

- Constitution 写明「TODO 不算完成」  
- Implement 分段，人工跑验收  
- Converge 专门找「声称完成但行为缺失」

### 4. 警惕一次生成上万行

功能切片太大，是代码爆炸的常见原因。  
**对策**：按用户故事 Implement；每次只要求「可演示的一小截」。

### 5. Analyze 不是走过场

有冲突却硬着头皮 Implement，等于把便宜错误留到昂贵阶段。  
**看见红灯就回流**，不要「先写了再说」。

### 6. 模型很重要，但流程更重要

同一套 Spec Kit，不同模型在「遵守约束 / 冗长度」上差异明显。  
流程不能替你选模型，但能让你更早发现模型跑偏。

### 7. 刷新模板前先备份

`specify init --here --force ...` 可能覆盖项目文件。  
**先保护** `.specify/memory/constitution.md` 与自定义 templates/scripts。

### 8. 人机分工别浪漫化

Spec Kit 提升的是「意图 → 实现」的可控性；  
**安全审查、产品判断、线上责任**仍然在人。

## 十、团队两周落地清单（可直接抄）

### 第 1 周：学会开车

- [ ] 安装 `specify-cli` 并在小仓库 `init`  
- [ ] 写一版不超过 2 页的 Constitution  
- [ ] 用最短主线做完一个玩具功能  
- [ ] 强制走一次 Clarify + Analyze（即使功能很小）  
- [ ] 记录：哪些步骤最耗时、哪些产物最有用  

### 第 2 周：开进真实车流

- [ ] 选一个存量仓库的真实小功能（最好 3～5 天量级）  
- [ ] Spec 由产品确认，Plan 由架构确认  
- [ ] Implement 按用户故事分段合并  
- [ ] 用 Converge 作为「可宣布完成」的门禁  
- [ ] 复盘：返工次数、缺陷类型、文档是否仍可信  

### 可以设立的团队约定

1. 没有 Spec，不进 Plan  
2. 没有 Analyze（或明确豁免），不进 Implement  
3. 没有 Converge，不叫 Done  
4. 需求变更必须先改 Spec，再动代码

## 十一、常见问题 FAQ

**Q1：Spec Kit 支持哪些语言？**  
A：流程与语言无关；具体代码能力取决于你用的 AI 助手与模型。

**Q2：必须把所有命令都跑一遍吗？**  
A：不是。最短主线即可开工；Clarify / Checklist / Analyze 是质量闸门，越复杂越该开。

**Q3：适合大型企业吗？**  
A：适合。越是有合规、安全、设计系统约束的组织，越需要把约束写进 Constitution / Plan。可用 Extensions、Presets、Bundles 做组织级定制。

**Q4：和 Cursor / Copilot / Claude Code 是什么关系？**  
A：它们是「司机」（编码助手），Spec Kit 是「导航仪」（流程与产物）。可以组合，不互斥。

**Q5：已经有 PRD 了，还要 Specify 吗？**  
A：建议把 PRD 翻译/收敛成 Spec Kit 的 `spec.md` 结构——因为后续 Plan/Tasks/Implement 认的是这套产物，不是附件 PDF。

**Q6：复杂业务逻辑怎么办？**  
A：拆成多个功能目录 / 多个用户故事，分别 Specify；用 Analyze 看跨故事一致性，用 Converge 收口。

**Q7：生成代码还要不要人审？**  
A：要。SDD 把人从「码农打字」推向「规格法官 + 增量验收员」，不是从责任里消失。

**Q8：什么时候不该用？**  
A：纯探索性 doodle、10 行脚本、一次性扔掉的实验——直接 prompt 可能更爽。等「开始在乎对错」时再切换到 Spec Kit。

## 十二、上手建议（高阅读量文章的共识浓缩）

1. **先小后大**：周末项目跑通，再上生产功能。  
2. **宪法别敷衍**：可判定 > 好听。  
3. **Specify 禁止提早选栈**：保护需求纯度。  
4. **每阶段人工把关**：AI 产文档，人做判决。  
5. **复杂需求必开 Clarify / Analyze**。  
6. **用 Converge 闭环**：否则 SDD 会退化成「多写了三份说明」。  
7. **分段实现**：对抗上下文爆炸与虚假完成。  
8. **变更先改 Spec**：让真相源始终可信。

## 十三、一分钟速记

- **SDD** 是思想：规格可执行，代码为规格服务。  
- **Spec Kit** 是工具包：把思想变成命令、模板与产物链。  
- **Specify CLI** 是入口；**`/speckit.*`** 是日常驾驶盘。  
- **关系**：Constitution 约束全局 → Spec 定目标 → Plan 定路径 → Tasks 定切片 → Implement 交付 → Converge 对齐。  
- **质量门**：Clarify / Checklist / Analyze 用来便宜地发现错误。  
- **最值场景**：存量加功能、严肃的新项目、遗留重建。  
- **口诀**：**先对齐意图，再生成实现；先写清楚，再写代码；先改规格，再改世界。**
